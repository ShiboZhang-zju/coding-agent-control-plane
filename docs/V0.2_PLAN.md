状态：**已完成其范围 / 历史文档（Superseded）**
适用阶段：**v0.2 阶段**（本地单用户控制平面：常驻 Runtime、持久队列、项目注册、
内容绑定审批、基础产物验收）。该范围已实现，本文档保留作为历史记录。

> **后续路线图请见 [PROJECT_CENTRIC_ROADMAP.md](PROJECT_CENTRIC_ROADMAP.md)。**
> 产品定位已从"单人控制平面"升级为 Project-Centric LD System；本文档中

基线：`poc/codebuddy-adapter@2f4b33b`
日期：2026-10-29
目标用户：在一台受信任的本地工作站上，同时管理多个项目和多种 Coding Agent 的单个操作者

## 1. v0.2 的一句话目标

把当前“可证明的控制平面内核 + CodeBuddy Adapter”变成一个可以常驻运行、崩溃后恢复、
通过 CLI/API 操作、能调度多个项目并接入第二种 Worker 的本地单用户系统。

v0.2 不是一个聊天窗口集合，也不以 Dashboard 为第一交付物。它首先要做到：

> 操作者提交带验收条件的工作项后，可以离开终端；控制平面负责安全派发、持续观测、
> 异常对账、验收和聚合，只在真正需要人决定时打断操作者。

### 2.1 本次审阅发现的结构债

这些是源码事实，不代表对应能力已经失效，但必须在接第二个 Adapter 前清掉：

| 结构债 | 当前表现 | v0.2 处理 |
|---|---|---|
| 控制平面仍有厂商泄漏 | `plane.py` 读取 `metadata["codebuddy"]`；`verify.py` 写死 `.codebuddy/` 忽略前缀 | Adapter 返回规范化 metadata 和 bookkeeping 路径，控制平面不识别厂商名 |
| `adapters/base.py` 的说明文字出现厂商名 | 与仓库自己的边界规则冲突 | M0 加静态边界测试并清理 |
| `ControlPlane` 只持有一个 Adapter | 不能由一个 Runtime 同时路由多个 Worker | 在 Runtime 引入 `WorkerRegistry`；现有单 Adapter 核心作为执行单元保留 |
| 没有正式服务生命周期 | 目前只能由脚本/调用方手动执行 refresh | M2 引入 Runtime、Scheduler、Reconciler |
| 测试与证据生成混在脚本中 | T16–T20 会直接覆盖 evidence 文件 | 离线 pytest 与 live evidence runner 分离 |
| SQLite 多进程 claim 已验证，迁移回滚未验证 | 多进程只有一个 claim winner | M1 + T24 继续覆盖迁移 |
| 验收与 Worker 刷新同步执行 | 大仓库扫描或测试命令可能拖慢观测循环 | v0.2 将终态验收放入独立、限时的 verifier job |

## 3. 产品边界

### 3.1 v0.2 必须交付

1. **常驻 Runtime**：启动、停止、健康检查、优雅退出和重启恢复。
2. **多项目注册表**：明确哪些仓库允许被操作、各项目的默认策略和并发上限。
3. **持久任务队列**：工作项、依赖、优先级、目标 Worker、attempt 与验收条件全部落库。
4. **Scheduler + Reconciler**：自动派发 ready 工作项；高频刷新已知任务，低频发现孤儿任务。
5. **多进程安全 Ledger**：至少两个控制进程竞争同一任务时不能重复派发。
6. **统一 Adapter 运行时**：按能力选择 Worker；接入第二个 Adapter 并通过契约测试。
7. **可扩展验收器**：文件/Git 断言之外，支持命令、测试、JSON Schema 和 diff 白名单。
8. **操作面**：稳定的本地 HTTP API 和 CLI，覆盖提交、查询、取消、审批、重试和诊断。
9. **事件与审计导出**：每次状态变化、人工决定、派发意图和验收结果可追溯、可脱敏导出。
10. **最小通知机制**：只报告完成、失败、需要审批、状态不确定和 ledger 降级。

### 3.2 v0.2 明确不做

- 不做多用户、RBAC、云端控制面或跨机器集群；
- 不做可视化工作流编排器和通用 DAG 语言；
- 不承诺任意不可信代码的安全沙箱；
- 不自动合并 PR、部署生产环境或使用生产凭据；
- 不把 SSE 当作唯一事实来源；
- 不允许 Worker 自己的终态绕过控制平面验收；
- 不在 Runtime 稳定前投入完整 Dashboard。

## 4. 目标架构

```text
CLI / Local API client
          |
          v
+-----------------------------+
| Control Plane Runtime       |
|                             |
| API  -> Application Service |
|              |              |
| Scheduler / Reconciler      |
|              |              |
| Policy / Approval / Verify  |
+--------------+--------------+
               |
       +-------+--------+
       | Worker Registry |
       +---+----------+--+
           |          |
     CodeBuddy     Worker #2
      Adapter       Adapter
           |          |
       jobs/worktrees/processes

SQLite Ledger = intent + attempts + observations + evidence + approvals
Filesystem/Git = artifacts to be independently verified
```

### 4.1 分层约束

- `adapters/base.py` 保持厂商无关；新增 Worker 只在 `adapters/<vendor>/` 放专有知识。
- `controlplane/` 只拥有领域状态、策略、调度、验收和持久化，不感知厂商字段。
- HTTP/CLI 放在新包 `runtime/` 与 `cli/`，不得直接读 Worker 私有磁盘结构。
- SQLite 是 v0.2 唯一事实账本；SSE、日志和 Worker 列表只是观测源。
- API handler 不直接派发 Worker，所有变更先写入 intent，再由应用服务/调度器执行。
- `WorkerRegistry` 只按 Adapter 名称和 capability 路由，不把任何厂商分支写进控制平面。

### 4.2 状态继续分层，不合并成一个字符串

v0.2 保留当前三个独立问题：

1. `TaskState`：Worker 现在声称自己处于什么执行状态；
2. `Verdict`：控制平面是否验收通过；
3. 新增 `WorkStatus`：工作项是否 `ready / blocked / dispatched / needs_human / complete`。

调度状态不得塞进 `TaskState`，否则“依赖未完成”和“Worker 尚未启动”会再次混在一起。

## 5. 领域模型与 Ledger 演进

### 5.1 新增实体

| 实体 | 关键字段 | 用途 |
|---|---|---|
| `projects` | id、root、default_adapter、policy、concurrency_limit、active | 注册允许操作的项目根目录 |
| `work_items` | 保留现有字段；新增 project_id、priority、desired_status、retry_policy | 用户目标与调度意图 |
| `dependencies` | work_item_id、depends_on_id、condition | 仅支持“验收通过后解锁”的最小依赖 |
| `attempts` | 保留现有字段；新增 adapter、lease_id、dispatch_digest、exit_reason | 每次实际执行 |
| `leases` | work_item_id、owner、expires_at、heartbeat_at | 多进程抢占与崩溃恢复 |
| `observations` | attempt_id、source、observed_state、observed_at、payload | 将观测与控制命令分开 |
| `schema_migrations` | version、applied_at | 正式管理 SQLite 升级 |

`events`、`evidence`、`approvals` 继续使用现有模型；事件保持 append-only。

### 5.2 一致性规则

- 创建工作项、计算幂等键、获取 lease 必须在单个 SQLite 事务中完成；
- 派发前持久化 `dispatch_intent`；派发后再绑定 worker job id；
- 进程在两者之间崩溃时恢复为 `dispatch_unknown`，绝不自动再 POST；
- lease 到期只表示调度器失联，不表示 Worker 任务死亡；
- 自动重试只允许发生在“能够证明没有创建 Worker job”或“旧 attempt 已明确终止”之后；
- approval digest 继续绑定 prompt、cwd、policy、assertions，并扩展绑定 adapter 与项目策略版本。

## 6. Scheduler / Reconciler 设计

### 6.1 调度循环

每轮按以下顺序执行：

1. 恢复过期 lease 和 inflight intent；
2. 选出依赖已通过、项目启用、审批满足的 `ready` 工作项；
3. 应用全局、项目、Adapter 三层并发限额；
4. 按 `priority DESC, created_at ASC` 获取 lease；
5. 运行策略校验、路径校验和 baseline 捕获；
6. 只调用一次 Adapter `dispatch()`；
7. 持久化 attempt/job 映射或进入 `dispatch_unknown`；
8. 释放调度 lease，观测职责转交 Reconciler。

v0.2 不做复杂公平队列；同优先级下使用 FIFO，并保证一个繁忙项目不能突破自己的并发上限。

### 6.2 对账循环

- 已知运行任务：默认 5 秒刷新，连续失败指数退避至 60 秒；
- 终态任务：立即做一次产物采集与验收，然后停止高频刷新；
- 全量孤儿扫描：默认 60 秒一次，失败不改变已知任务状态；
- SSE：只用于降低可见延迟，收到事件后触发单任务刷新；不直接形成最终状态；
- `lost`：继续要求独立进程/连续扫描证据；
- Runtime 启动：先 `recover_inflight()`，再开始任何新派发。

### 6.3 重试策略

默认 `max_attempts=1`。只有工作项显式配置后才允许重试：

- `dispatch_unknown`：禁止自动重试；
- `failed/cancelled/lost`：旧 attempt 明确终止后，可按策略创建新 attempt；
- `rejected`：默认需要人修改 prompt/断言，不能原样自动重跑；
- `inconclusive`：需要补断言或人工决定，不能当成功；
- 每次重试生成新的 attempt，旧 job/session/evidence 永不覆盖。

## 7. Adapter v0.2 契约与第二 Worker

### 7.1 先建立契约测试，不先写第二个 Adapter

新增 `tests/contract/`，任何 Adapter 都必须通过同一组测试：

- capability 声明与实际行为一致；
- dispatch 每次调用最多创建一个 job；
- get/list/reconcile 不可达时返回“未知”而不是伪造成功；
- cancel 的终态与控制平面 verdict 分离；
- resume 只宣称对话恢复，不宣称执行恢复；
- event 是否可重放必须显式声明；
- artifact 枚举只返回实际观测到的产物；
- Adapter 重建后仍能通过 worker job id 查询；
- 所有厂商原始字段只能进入 `TaskSnapshot.metadata`。

契约测试分为：完全离线的 fake worker、故障注入测试、需要显式开启的 live test。

### 7.2 第二 Adapter 选择门槛

先用 1–2 天做 Codex CLI 与 Claude Code/ACP 的能力探针，按以下硬门槛选择：

1. 能非交互派发并立即获得稳定句柄；
2. 能按句柄查询当前状态，或 Adapter 能可靠持久化本地进程句柄；
3. 能取消，且能够区分对话恢复与执行恢复；
4. 能定位工作目录、worktree 和可验收产物。

优先选择满足门槛更多、需要私有协议更少的一方。选型结论必须进入新的 capability matrix，
没有 live evidence 的能力标记为 `unverified`。无论选谁，都不得为第二个 Worker 修改
`controlplane/` 的厂商无关语义。

## 8. 验收器 v0.2

新增以下断言类型：

| 断言 | 行为 |
|---|---|
| `command_succeeds` | 在验收环境运行固定 argv，记录退出码与脱敏输出摘要 |
| `test_command` | 与上项类似，但在汇总中单独显示测试数量/失败 |
| `json_schema` | 指定 JSON 文件符合内置 schema |
| `git_diff_allowlist` | 只允许修改声明的路径/前缀 |
| `git_no_untracked` | 不允许遗留未声明文件 |
| `file_sha256` | 产物哈希匹配预期值 |

约束：

- 验收命令使用 argv，不接受未经审批的 shell 拼接；
- 验收器自己的执行也必须有超时、输出上限和脱敏；
- baseline 捕获失败时 verdict 为 `inconclusive`，不能降级为“只看文件存在”；
- worktree 之外的副作用继续优先判 `rejected`；
- v0.2 只支持本地可信仓库；OS 级隔离是独立能力，不用“worktree”冒充。

## 10. 安全模型

### 10.1 v0.2 的安全承诺

- 默认只监听 loopback；
- 只允许操作已注册且解析后仍位于允许根目录内的项目；
- 默认策略仍为 `agent + worktree + acceptEdits`；
- 无隔离 shell 始终是 high risk，要求内容绑定的一次性审批；
- ledger 降级时所有变更操作 fail-closed；
- 日志、事件和 evidence 落盘前统一脱敏；
- 不读取或提交完整 transcript、Token、Cookie、Authorization Header；
- Runtime 不自动 merge、push 或部署，除非未来引入独立且显式的策略。

### 10.2 OS 级隔离

Windows 受限账户/令牌 + NTFS ACL 做一个独立 spike，验证 Worker 是否仍可正常登录、访问 Git
和模型服务，同时无法写出允许根目录。该能力未通过 live evidence 前：

- capability 必须是 `unverified/unsupported`；
- 系统只能宣称“可信本地自动化”，不能宣称“可运行不可信代码”；
- 越界检测是验收防线，不是安全边界。

## 11. 可观测性与通知

- 结构化日志字段至少包含 `work_item_id / attempt_id / adapter / event_type / duration_ms`；
- 错误输出默认截断，敏感字段使用现有 `redact()` 规则并集中到厂商无关工具中；
- `/healthz` 只表示进程活着；`/readyz` 还要求 ledger 可写、迁移完成、scheduler 已启动；
- 通知只针对：`verified`、`rejected`、`needs_human`、`dispatch_unknown`、ledger degraded；
- 普通 running/轮询成功不通知，防止一个操作者被状态噪声淹没。

## 12. 里程碑与实施顺序

### M0：功能垂直切片（已完成）

- 常驻 Runtime、优雅停止、启动时 inflight 恢复；
- 队列派发、已知任务刷新、孤儿扫描三条独立循环与故障退避；
- 持久 ready 队列、优先级、Adapter 并发上限；
- `BEGIN IMMEDIATE` 原子 claim，两个独立进程只能有一个派发者；
- 高风险 queued work 自动进入审批箱，批准后才 ready，成功派发后单次消费；
- 本地 CLI：enqueue/list/show/summary/events/approval。

退出证据：T21–T25 全部 Pass。

### M1：项目注册、依赖与恢复（4–6 人日）

- projects/dependencies/lease/observation 正式实体；
- 只允许注册项目根目录内的任务进入 ready；
- 最小依赖解锁、手动 retry 和 attempt 上限；
- Runtime 重启、claim 进程崩溃、migration rollback；
- 多项目与 Adapter 两层并发/公平性。

退出条件：Runtime 重启两次仍能继续管理既有任务；依赖未验收时绝不派发。

### M2：本地 HTTP API（3–5 人日）

- 项目、任务、审批、summary、events、health API；
- 现有 CLI 改为 API client，保留 ledger-only 诊断模式；
- 请求幂等、错误码和 loopback 随机 token；
- API 黑盒测试。

退出条件：操作者无需 Python REPL 或直接访问 SQLite 即可完成完整任务生命周期。

### M3：Adapter 契约与第二 Worker（4–7 人日）

- fake/fault/live 三层契约测试；
- Codex 与 Claude Code/ACP 能力 spike；
- 实现胜出者 Adapter；
- 用同一组任务验证 CodeBuddy 与 Worker #2。

退出条件：第二 Adapter 接入没有修改控制平面厂商无关语义，并通过 live evidence。

### M4：验收、安全与运行加固（3–5 人日）

- 命令/测试/schema/diff 断言；
- 项目根目录约束与路径穿越测试；
- Windows OS 隔离 spike；
- 日志脱敏、evidence 导出、最小通知。

退出条件：失败、越界、旧产物、观测中断均不能形成假成功。

### M5：工程化与 v0.2 验收（3–5 人日）

## 14. v0.2 Definition of Done

只有同时满足以下条件才标记 v0.2：

- 一条命令启动 Runtime，一条命令完成诊断；
- 至少两个项目、两个 Adapter 能由同一 Runtime 管理；
- 所有派发都有 work item、attempt、policy、baseline、断言和可追溯事件；
- 重启、超时、断线、重复请求不产生静默丢失或盲目重复执行；
- Worker 的成功声明不能绕过验收；
- 高风险操作没有匹配审批就不会调用 Worker；
- ledger 降级时只读、明确告警；
- T21–T31 有脱敏 evidence，失败项如实标记 Fail/Blocked/Unverified；
- 文档明确区分 worktree 隔离和 OS 安全隔离；
- 没有凭据、原始 transcript 或服务密码进入 Git 历史。
